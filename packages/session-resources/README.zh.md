**一个会话动过什么的账本。** 在「对话」「轨迹」旁边加一个「资源」标签页，列出这个会话**产出**的文件和它用作**来源**的文件。点一行即可打开该文件。

```sh
dsh plugin --profile web add -w dsh-plugin-session-resources
```

## 安装

**`-w` 是必需的。** profile 目录是个 pnpm workspace 根，不带 `-w` 时 pnpm 会以 `ERR_PNPM_ADDING_TO_ROOT` 拒绝，什么都不会装上。

**每个 profile 要各装一次。** 标签页只出现在装了这个包的 profile 里，所以桌面端需要单独装：

```sh
dsh plugin --profile desktop add -w dsh-plugin-session-resources
```

**装的时候不索要构建授权。** 浏览器半边是手写的纯 JS，经应用自己的模块加载器载入，没有构建步骤也没有 `prepare` 脚本 —— pnpm 不会要求你为这个包的代码在安装时执行放行。

**没有任何需要配置的东西。** 账本是从会话日志里已有的信息折叠出来的。

之后更新：

```sh
dsh plugin --profile web update dsh-plugin-session-resources
```

## 它不是文件浏览器

它从不列目录、不遍历树、不读磁盘。它报告的是**这个会话做了什么**：两份清单，全部由会话日志里已有的工具活动推导而来。你这个会话没碰过的文件不会出现；你碰过的文件，即使之后从磁盘删掉，它那一行依然在。

它也不同于 harness 内建的产出文件行。那一行是**按轮次**的，挂在收尾消息下面，并且按设计只计成功的写操作 —— 读操作不贡献任何东西。这个标签页是**按会话**的，而且保留读操作，因为「这份工作参考了哪些文件」是问题的另一半，眼下没有别的东西回答它。

## 两份清单的含义

**产出**是一次已结算、成功的写操作所写的文件。**来源**是一次已结算、成功的读操作所打开的文件。

同一路径在一份清单里最多出现一次，按最早贡献它的那次调用在日志里的位置排序，每行标出促成它的各个工具 —— 所以一个先被 `write` 写出、又被 `edit` 改过的文件是一行，标着 `write · edit`。

被两种角色同时认领的路径**只列在产出下**：会话写过的文件就是交付物，无论中途是否也读过它。列两次会把一个文件报成两份资源。

行按目录分组。位于会话工作区内的目录只显示根以下的那部分，而工作区根自己不显示任何标题，因为在每个分组上重复它正是这里要去掉的噪音。

### 工作区之外的文件会被标出来

不在会话工作区之下的目录会保留绝对路径，并带一个**工作区外**标签。

这个标签回答的是第一次打开这个标签页时最容易冒出来的疑问：*一个会话为什么会列出别处的文件？* 因为这个会话确实动过它们。harness 的文件效果模式管的是**写**——`workspace-write` 把写限制在工作区及其临时目录内，**读不受限制**；`danger-full-access` 两者都不限制。所以一个会话读到任何地方都是合法的，而一旦获得 full access 或一次批准的提权，它也能写到任何地方。这个标签页没有放宽任何权限，它只是让已经发生的事变得可见。

比较逻辑是刻意保守的。工作区相对路径按构造就在内部 —— 它之所以是相对的，正因为要相对会话根解析。Windows 拼写按大小写不敏感比较，因为为一个盘符的大小写去标记工作区内的目录，是在最不该谎报的信号上谎报。工作区根未知时一律不标记，而不是凭猜测标记。

## 一次调用如何成为一个条目

判定依据是**渲染意图，而非工具名字**：写操作是 `diff` 卡片，或 `kind` 为 `edit` 的通用卡片（`str_replace_editor` 的插入就是这个形状）；读操作是 `read` 卡片，或 `kind` 为 `read` 的通用卡片。看意图而不看名字，意味着一个还没被写出来的文件工具，只要声明自己在做什么，就能自动进入这个账本 —— 这里没有任何名单需要维护。

`tool/call` 开始折叠，`tool/result` 完成它。这个方向是被迫的而非随意选择：写操作的文件身份只可能存在于调用视图里，因为 `kind: 'edit'` 的通用卡片在调用时的 `locations` 里点名文件，而它的结果视图一个都不点。但结果才是决定这份贡献是否算数的东西 —— 还没结算的调用什么都没写，而失败的调用不能认领文件，即便它的工具在调用时已经展示了一份 diff。**两种失败信号都被采纳**：内部失败身份（`data.error`，工具抛了异常）和面向模型的标记（`isError`，工具报告了失败）。

`card` 以下的每个字段都是不可信的。线上 schema 只锁定 `for` 判别式和「存在一个带 card 标记的对象」，所以版本不匹配或异常插件可以送来一个没有任何路径的 `diff` 卡片，或者一个没有 `path` 的 `locations` 条目。分类器按结构收窄并丢掉读不懂的部分，所以一个畸形视图的代价是少一行，而不是整个标签页坏掉。

## 打开文件

点击一行会把路径经与工具行相同的路由交给宿主，工作区相对路径先按会话根解析。打开失败时保持静默：路径不可用时原生应用会自己弹对话框，而账本里的一行不是报告这件事的地方。

## 已知限制

- **账本只覆盖已加载的历史窗口。** 如果某次调用的 `tool/call` 已经滚出窗口，它会留下一个待定上下文、不贡献任何东西，直到更早的一页提供它的起点 —— 所以长会话最早的文件在你往回翻之前是缺失的。要做全需要宿主侧的投影，而不是浏览器端的折叠。
- **检索与网页结果不计入。** `glob`/`grep` 的路径和 `web_search` 的来源确实是真实出处，但一次检索调用可以点名几百个没人打开过的路径；把它们折进来会淹没会话真正用到的文件。
- **删除与移动不贡献任何东西。** 被删掉的文件不是交付物，移动的目的地不在已验证的写操作词汇表内，所以两者都是缺席而不是猜测。
- **只被 shell 命令碰过的文件不可见。** 终端卡片点名的是工作目录而不是文件，所以一次写文件的重定向没有可折叠的位置信息。
- **模型看不到这里的任何东西。** 这个标签页不加工具、不加提示词段落、不发请求，无法从会话里查询它。

## 不卸载而关掉标签页

在 profile 自己的 `cordis.patch.yml` 里按 id 覆盖这一行 —— 别再 `insert` 一遍，同一个 id 插两次会让启动直接失败（`duplicate loader entry id`）：

```yaml
- id: session-resources
  disabled: true
```

## 本地开发

从本地检出安装需要 `file:` 前缀，它是拷贝语义而非链接语义：

```sh
dsh plugin --profile web add -w "file:/path/to/dsh-plugins/packages/session-resources"
```

改完源码后刷新那份拷贝：

```sh
dsh plugin --profile web install
```

宿主半边是故意空的。它存在是因为 profile 通过 loader 行来组合包，而一行需要一个模块去挂载；正是这一行把包带进组合，也正是这一点让网页应用去读 `dsh.client` 声明。
